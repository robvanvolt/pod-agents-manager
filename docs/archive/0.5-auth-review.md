# Feedback on the 0.5 auth-sharing slice

This is a code review of the `wip(0.5): auth-sharing scaffolding` commit on
`codex/0.5-auth-sharing` (commit `56c1a66`). Hand this verbatim to whichever
agent (GPT 5.5 or otherwise) picks up the next iteration so the analysis
doesn't have to be re-derived.

## What's already right — keep as-is

- Architecture: separating *authorization* (sessions, roles, audit) from
  *authentication method* (token now, passkey later). Passkeys will plug
  into the same `authState` / `authContext` / `requireOperator` plumbing
  without a rewrite.
- Bootstrap token via `pod server token rotate` matches the roadmap's
  recovery/headless promise.
- Security primitives: SHA-256 hashed bootstrap token, hashed sessions,
  `subtle.ConstantTimeCompare`, `0o600` perms, `authMutex`, HttpOnly +
  `SameSite=Strict` cookie, IP and UA in audit entries, role-tagged
  audit on both allow and deny paths.
- Decision to merge `codex/0.4-inbox-workflows` into the 0.5 branch first
  so the gated write paths include `/api/instruct`.

## Block 0.5 on these two

The release is explicitly about *sharing the dashboard over LAN*. Both of
these are concrete weaknesses for that exact threat model.

### 1. CSRF protection on every write handler

`SameSite=Strict` mitigates *most* of CSRF, but it's fragile in practice
(some browsers carry Strict cookies on top-level navigations from
external origins, link-handler quirks, etc.). The 0.5 release threat
model is "another device on the same Wi-Fi attempts a cross-origin
write" — the canonical CSRF case.

Add either:

- An `Origin` / `Host` allowlist check on every write handler. Reject
  if `r.Header.Get("Origin")` is set and doesn't match
  `r.Host` (and the handful of bound LAN IPs surfaced by
  `localIPs()`). Allow empty Origin (curl, fetch from same origin) only
  when `Sec-Fetch-Site` is `same-origin` or absent.
- *or* a CSRF token tied to the session, returned by
  `/api/auth/status`, required as `X-Pod-CSRF` on POSTs.

I'd lean toward the Origin check — it's ~30 lines, no UI changes, and
captures the actual threat. Audit any denial as `csrf_blocked` so the
log shows it.

### 2. Rate-limit `/api/auth/login`

Bootstrap token guards everything. There's no lockout, no per-IP
throttle. A LAN attacker can brute-force at line rate. Constant-time
comparison protects the comparison itself but not the oracle.

Add a simple in-memory rate limiter keyed by `clientIP(r)`:

- 10 attempts per IP per minute — hard cap.
- After 5 consecutive failures, exponential backoff (sleep 1s, 2s, 4s,
  8s, 16s before the response).
- Reset on a successful login.

In-memory is fine — the dashboard is a single process, sliding-window
counters in a `sync.Mutex`-guarded map are ~40 lines. Audit each
rate-limited rejection as `auth.login` / `result: rate_limited`.

## Should-fix before 0.5, but won't block it

### 3. `Secure` cookie flag is unconditionally off

Correct for `http://` LAN. But people front the dashboard with caddy /
nginx + HTTPS — common deploy. Cookie shouldn't leak over plaintext
when TLS is available. Make it:

```go
Secure: r.TLS != nil || os.Getenv("POD_SERVER_FORCE_SECURE_COOKIE") == "1"
```

The env var lets a reverse-proxy deploy force the flag even though the
Go server itself terminates plain HTTP behind the proxy.

### 4. Test coverage is one happy-path test

`TestBootstrapTokenCreatesOperatorSession` confirms a correct login
works. The 0.5 surface needs at least these added — each is ~10 lines:

- `TestLoginRejectsWrongToken` — `verifyBootstrapTokenAndCreateSession`
  returns `invalid bootstrap token`, no session is created.
- `TestExpiredSessionDoesNotGrantOperator` — write a session row with
  `ExpiresAt` in the past, `currentAuthContext` returns `viewer`.
- `TestLogoutRevokesSession` — login, logout, then try to use the same
  cookie; should be `viewer`.
- `TestRequireOperatorWritesAuditEntryOnDeny` — call a write endpoint
  unauthenticated, assert `audit.jsonl` gains a `result: denied` row
  with `role: viewer`.

Add a parallel bash test in `tests/run.sh` that exercises
`pod server token rotate` then `curl -d 'token=<x>'` against
`/api/auth/login`, checks the cookie comes back and the audit file
has the matching `auth.login` / `ok` entry.

### 5. README has nothing on first-time auth setup

A user opening the dashboard sees an "Unlock" button with zero context
on where the token comes from. The current JS `prompt('Dashboard
operator token')` is also a generic browser dialog — no copy-paste
affordance, no visibility toggle.

Add a short subsection to `README.md` (right after the "The dashboard"
section is the natural spot):

> **First-time auth setup.** The dashboard starts in viewer mode —
> stats and pod list visible, no write actions allowed. To unlock
> operator mode (create / start / stop / delete / instruct):
>
> ```bash
> pod server token rotate    # prints a one-time bootstrap token
> ```
>
> Click **Unlock** in the dashboard, paste the token. The session
> lasts 24 hours per browser. Lost the token? Run `pod server token
> rotate` again — it invalidates the old token, every active session
> stays valid until expiry.

Optionally replace the JS `prompt()` with a real `<input
type="password">` modal — better paste/visibility, ~30 lines of
HTML+JS. Not strictly required for 0.5 but cheap polish.

## Defer to 0.6 / 0.7 — don't try to fit into 0.5

These are real gaps but expanding 0.5 scope risks the release.

- **Audit log rotation.** Single JSONL grows forever. Add a one-line
  comment in 0.5 saying "rotation is a 0.6 task; don't depend on
  complete history."
- **`schema_version: 1` on `auth.json` and audit entries.** Cheap to
  add now, but if it slipped past 0.5, future migrations are
  recoverable.
- **A third role between viewer and operator** (e.g. `runner` —
  start/stop their own pods but no `delete-all`). The roadmap promised
  two roles; richer roles fit the 1.0+ "templates / sharing presets"
  arc better.
- **CLI session.** Today `pod start` etc. bypass the server, so the
  audit log only sees browser-originated writes. Misleading but not
  broken. 0.6 task: `pod` itself becomes audit-aware (writes a
  parallel `cli.audit.jsonl` or POSTs to the dashboard with a local
  session).

## Suggested commit shape

Keep the WIP commit (`56c1a66`) intact — it's already a clean
checkpoint. Stack the 0.5 finishing work as separate commits on the
same branch:

1. `feat(0.5): origin-based CSRF guard on write endpoints`
2. `feat(0.5): rate-limit /api/auth/login per IP`
3. `feat(0.5): conditional Secure cookie flag`
4. `test(0.5): negative-path coverage for auth and audit`
5. `docs(0.5): first-time auth setup section + UI tweak`

Then merge into `dev`, test on `ssh nuc` per the project workflow,
bump `version.conf` to `0.5.0`, fast-forward into `main`.

## On the 0.5.1 work that was layered on top

For context: I also stacked a 0.5.1 release on top of the WIP commit
on the same branch (`feat(0.5.1): sham OpenAI/Anthropic endpoints +
pod test command`, plus three small follow-ups for opencode / hermes /
nanocoder agent invocations). That's `pod test --all`, exercising
every agent against a built-in sham endpoint. It doesn't conflict
with the 0.5 auth work — the sham endpoints `/v1/*` are unauth'd by
design (they're a fixture for `pod test`). When the CSRF guard from
item 1 lands, make sure to either exempt the `/v1/*` paths or move
the sham endpoints under a separate path prefix that the guard
ignores.
