Overview

Pod Agents Manager documentation

pod turns a Linux box with rootless Podman into a multi-tenant home for local AI coding agents. Each agent instance runs in its own container with a persistent workspace, talks to your own OpenAI-compatible inference server, and is driven from one shell command or a LAN dashboard.

Mental model. One agent (claude, codex, pi, …) can have many instances (dev, alpha, …). Each instance is one container plus one workspace directory on the host. Nothing is shared between instances except read-only skills.

Shell-native

One Bash function, no daemon. Quadlet generates systemd units; Podman runs them rootless as your user.

Bring your own model

Any OpenAI-compatible endpoint — llama.cpp, vLLM, LM Studio, Ollama, MLX. No cloud account required.

Drop-in extensions

Agents, flavors, volume bundles, skills, templates, and benchmark tasks are all files in a directory.

Requirements

What you need

ComponentMinimumNotes
Linuxany modern distroTested on Debian 12, Ubuntu 22.04+, Fedora 39+. Pods need systemd, so this is the runtime host.
Podman4.4+ (5.8+ ideal)Rootless. pod masks the buggy podman-user-wait-network-online.service on 5.0–5.7 automatically.
systemd (user)requiredQuadlet turns *.container templates into user units. Run loginctl enable-linger $USER so pods survive logout.
Bash4+ on the hostThe lint/test suite also runs on macOS Bash 3.2 for development.
tmuxoptionalNeeded for pod tmux and pod batch tmux.
jqoptionalNeeded for pod bench scoring and JSON/CSV export.
Gonot requiredThe dashboard binary is built in a throwaway golang:alpine container if Go is missing.

You also need an OpenAI-compatible inference endpoint. On first run, missing POD_* values are prompted once and saved to ~/.pod_agents_config/.env.

Installation

Three ways to install

1. Stable channel (recommended)

The installer places ~/.pod_agents, seeds ~/.pod_agents_config/, and adds one source line to your shell rc.

curl | bash 
curl -fsSL https://raw.githubusercontent.com/robvanvolt/pod-agents-manager/main/install.sh | bash
exec bash -l
pod doctor
Name collision? If pod is already taken (CocoaPods), the installer offers a different name and records it in ~/.pod_agents_config/.cmd_name. Non-interactive installs can set POD_AGENTS_CMD=pods beforehand. Every help message adapts to the name you chose.

2. Homebrew

Installs as pod-agents so it never shadows CocoaPods. First run materializes your config tree; brew upgrade refreshes the code but keeps your .env and custom plugins.

brew 
brew install robvanvolt/tap/pod-agents-manager
pod-agents doctor

# optional shorter name
echo 'alias pod=pod-agents' >> ~/.bashrc

3. Development channel

Tracks the dev branch. Use this to try unreleased work; expect churn.

dev channel 
curl -fsSL https://raw.githubusercontent.com/robvanvolt/pod-agents-manager/dev/install-dev.sh | bash
exec bash -l

First session

getting started 
pod doctor              # verify podman, systemd, config, endpoint
pod config              # set or change POD_* values interactively
pod prebuild            # (optional) build every agent image up front
pod start pi dev        # create and start one pod
pod join pi dev         # attach to its tmux session
pod delete pi dev       # stop it and remove the workspace

Core concepts

How it fits together

Everything lives in two trees: a config tree you own, and one workspace directory per pod. There is no database and no daemon — state is files plus systemd units. 

~/.pod_agents                       the CLI itself (a sourced Bash function)
~/.pod_agents_config/
  .env                              your POD_* settings
  version.conf                      single source of truth for the version
  lib/NN-*.sh                       numbered CLI modules, sourced in order
  agents/<name>.sh                  agent plugins        → one CLI verb each
  flavors/*.containerfile           optional image layers
  volumes/*.volumes                 reusable mount bundles
  skills/<skill>/                   shared, read-only-mounted skills
  templates/*.conf                  preset pod configurations
  benchmarks/<task>/                benchmark task definitions
  batch/<id>/                       batch state, logs, progress
  server/                           Go LAN dashboard

~/Developer/<agent>-pods/<instance>/
  workspace/                        ↔ mounted at /workspace in the pod
  config/                           ↔ mounted at the agent's config path

~/.config/containers/systemd/<agent>@.container    Quadlet unit template

Lifecycle of pod start pi dev

  1. Build the image if missing — base image + chosen flavor + the agent's install steps, cached under ~/.cache/podman-containers/.
  2. Render a Quadlet pi@.container template with your volumes, ports, limits, and endpoint env vars.
  3. systemctl --user daemon-reload (only when the template actually changed) so Quadlet materializes the unit.
  4. Generate the agent's config file into the instance's config/ directory.
  5. systemctl --user start pi@dev.service — the pod is now running as pi-dev.
Data safety. pod remove disables the service but leaves the workspace on disk. pod delete removes the workspace too. Only delete destroys work.

The positional contract

Every action takes the same shape, and anything past the action is optional:

pod <action> [agent] [instance] [flavor] [volumes] [base]
            [--model NAME] [--endpoint URL] [--api-key KEY]
            [--ports HOST:CONTAINER[,...]] [--from-template NAME]
            [--memory VALUE] [--cpu VALUE] [--no-cache | --cached]

Running pod with no arguments opens an interactive menu that prompts for whatever is missing.

Configuration

Environment reference

All settings live in ~/.pod_agents_config/.env as POD_* variables. Edit the file directly or run pod config. Values are also exported into every pod (without the prefix) so agents can read them.

Core

VariableDefaultPurpose
POD_OPENAI_BASE_URL—Your inference endpoint, including the trailing /v1.
POD_OPENAI_API_KEY—Key sent as Authorization: Bearer. Any non-empty string works for most local servers.
POD_DEFAULT_MODEL—Model id. Comma-separate to offer several; the first is the default.
POD_DEFAULT_MODEL_CONTEXT_SIZE131072Context window declared to agents that need it (for example Codex's model_context_window).
POD_BASE_IMAGEalpinealpine, trixie-slim, or an explicit image reference.
POD_WORKSPACES_ROOT$HOME/DeveloperWhere <agent>-pods/<instance>/ directories are created.
POD_IMAGE_CACHE_ROOT$HOME/.cache/podman-containersBuild-context cache.

What each pod receives

The Quadlet template exports these into every container, so a wrapped agent works without extra configuration:

OPENAI_BASE_URL     OPENAI_API_BASE     OPENAI_API_KEY
ANTHROPIC_BASE_URL  ANTHROPIC_API_KEY   ANTHROPIC_MODEL
LLM                 DEFAULT_MODEL_CONTEXT_SIZE
FORGEJO_URL / _USER / _EMAIL / _TOKEN     (when configured)

ANTHROPIC_BASE_URL is your endpoint with /v1 stripped, which is how Anthropic-SDK agents (Claude Code, Command Code) are redirected at a local server.

Every action

Lifecycle

Per-invocation overrides

These flags work on start, restart, enter, and friends. They never touch .env — they apply to that one call.

FlagEffect

--endpoint URLPoint at a different inference server.
--api-key KEYOverride the key. --api_key and --apikey also accepted.
--ports H:C[,…]Publish container ports, e.g. --ports 3000:3000 for a dev server.

--memory VALUE / --cpu VALUEQuadlet MemoryMax= / CPUQuota=, e.g. --memory 2G --cpu 1.5.

Writing your own

Drop a <name>.sh into ~/.pod_agents_config/agents/. It's a Bash fragment defining two functions plus a few variables. No registry, no restart.

~/.pod_agents_config/agents/my-agent.sh 
# Where the agent keeps its config inside the container. This directory is
# bind-mounted from ~/Developer/my-agent-pods/<inst>/config/, so it persists.
AGENT_VOLUME_CONFIG_PATH="/root/.config/my-agent"

# Optional: where the shared read-only /srv/skills mount is symlinked to.
AGENT_SKILLS_SUBPATH="skills"

# Optional but recommended: one-shot invocation used by `pod batch`,
# `pod test`, and `pod bench`. $PROMPT is injected per run. Omit this and the
# agent is interactive-only.
AGENT_BATCH_INVOKE='my-agent --print "$PROMPT" --yes'

agent_build_containerfile() {
    local build_dir="$1" flavor="$2"
    # Writes the shared Node base + your chosen flavor. Pass a third argument
    # to force a base, e.g. "trixie-slim" for glibc-only binaries.
    write_base_node_containerfile "$build_dir" "$flavor"
    cat <<'EOF' >> "$build_dir/Containerfile"
RUN npm install -g my-agent && npm cache clean --force
CMD ["tail", "-f", "/dev/null"]
EOF
}

agent_generate_config() {
    local config_dir="$1" action="$2"
    # "update" means "preserve the user's existing config" — always return
    # early, or `pod update` will clobber their customizations.
    [ "$action" = "update" ] && return 0

    local first_model="${DEFAULT_MODEL%%,*}"
    cat <<EOF > "$config_dir/config.json"
{ "baseUrl": "$OPENAI_BASE_URL", "apiKey": "$OPENAI_API_KEY", "model": "$first_model" }
EOF
}

# Optional: runs once per `pod update` cycle, before rebuilding.
agent_pre_update() { podman pull docker.io/myorg/my-agent:latest; }
Two gotchas worth knowing. (1) Agents whose binary is glibc-linked need write_base_node_containerfile "$build_dir" "$flavor" "trixie-slim" — the default Alpine base uses musl. (2) If the CLI refuses to act without approval prompts, install a small wrapper script that injects its bypass flag, the way claude.sh and codex.sh do.

Skills

Shared, write-once capabilities

~/.pod_agents_config/skills/ is mounted read-only at /srv/skills in every pod, then symlinked into each agent's expected skills path. Update a skill once and every agent sees it immediately.

A skill is a directory with a SKILL.md whose front matter tells the agent when to use it:

---
name: roll-dice
description: Roll dice using a random number generator. Use when asked to
  roll a die (d6, d20, etc.) or generate a random dice roll.
---

To roll a die, use:

```bash
echo $((RANDOM % <sides> + 1))
```

Shipped skills: roll-dice (trivial example), paper-lookup (search 22M scientific papers), forgejo-workflow (create a repo and push, using your POD_FORGEJO_* token), and web (browse via a CDP service).

Templates & flavors

Presets and image layers

Templates

A template is a .conf file of POD_TEMPLATE_* values that pre-fills the flags for a common workflow.

# ~/.pod_agents_config/templates/web-app.conf
POD_TEMPLATE_FLAVOR="bun"
POD_TEMPLATE_PORTS="3000:3000"
POD_TEMPLATE_MEMORY="4G"

# then:
pod start codex ui --from-template web-app

Shipped: web-app, research, triage, refactor.

Flavors

A flavor is a Containerfile fragment appended to the base image — use it for toolchains your agent needs. Shipped: bun, uv. Pass all (the default) to layer every flavor, or a single name.

Volume bundles

A .volumes file is a list of Podman volume specs mounted into the pod — handy for sharing a model cache or dataset across agents.

Batch prompting

Fan a prompt list across the fleet

batch 
pod batch prompts.txt                       # every running pod
pod batch pi prompts.txt                    # only `pi` pods, sequentially
pod batch pi dev prompts.txt --concurrent    # one pod, prompts in parallel

pod batch stats                             # progress + ETA per runner
pod batch tmux                              # live log per active runner
pod batch log [id]                          # follow or dump a batch log
pod batch list                              # active batch ids (--all for finished)
pod batch stop <id>                         # SIGTERM the batch's runners

Input is one prompt per line (# comments ignored), or JSON — [{"prompt":"…"}, …] or ["…", …]. Runners are detached with nohup, so they survive your shell exiting.

State lives under ~/.pod_agents_config/batch/<id>/: a copy of the input, meta.conf, one runner script and pid per pod, progress/<pod>.prog (read by batch stats), per-pod logs, and done.<pod> markers. batch list and batch stats hide finished and cancelled batches by default.

Benchmarks

Compare agents on the same task

pod bench runs one task across your running pods, judges each artifact with an LLM against a rubric, and produces a comparable table. Runs are sequential by design: on one local inference server, parallel runs contend for the GPU and every wall-clock number becomes meaningless.

bench 
pod bench list                              # available tasks
pod bench run portfolio-single-file         # every running pod with a headless mode
pod bench run portfolio-single-file codex   # just one agent
pod bench results portfolio-single-file     # comparison table
pod bench export portfolio-single-file --csv > results.csv

Defining a task

Three files in ~/.pod_agents_config/benchmarks/<task>/:

FileContents
task.confBENCH_DESCRIPTION, BENCH_ARTIFACT (the file the agent must produce), BENCH_TIMEOUT in seconds.
prompt.mdSent to each agent verbatim as $PROMPT.
criteria.mdThe rubric handed to the judge LLM. Be specific and point-based.

Results are stored per run under benchmarks/<task>/runs/<id>/<pod>/ — meta.json (wall-clock, exit code, artifact size, and token counts where the agent exposes them), judge.json (score + rationale + judge model), the captured output.log, and a copy of the artifact itself. Everything is diffable and easy to share in a PR.

Judge honestly. By default the judge is the same local model that did the work, which is convenient but self-favouring. For numbers you'd publish, set POD_BENCH_JUDGE_* to a stronger or different model and say so alongside the results.

Dashboard & auth

The LAN dashboard

pod server start builds a small static Go binary (in a throwaway golang:alpine container if you have no Go) and runs it natively on the host — no podman-in-podman, no socket mounts. It binds 0.0.0.0 and prints every reachable LAN URL.

Features: live stats with CPU/memory sparklines, idle/running activity badges, a create-pod form, start/stop/restart/delete, an interactive terminal over WebSocket, journal streaming, batch progress and export, the instruction inbox, notes and tags, notification center over SSE, and a PWA install prompt for phones.

First-time auth

The dashboard starts in viewer mode — stats and pod lists are readable, but every write is locked. To unlock operator mode:

unlock 
pod server token rotate    # prints a one-time operator token
pod server restart

Click Unlock in the dashboard and paste the token. Sessions are HttpOnly cookies; you can then register a passkey for future logins. Lost the token? Rotate again — the old one dies, active sessions live until expiry.

Security model

  • Writes require operator role; reads are gated by the API key.
  • Origin/Host checking on every write handler (CSRF), audited as csrf_blocked.
  • Per-IP login rate limiting with exponential backoff.
  • Secure cookie flag when served over TLS or when POD_SERVER_FORCE_SECURE_COOKIE=1.
  • Every write attempt appended to server/audit.jsonl, with rotation and pruning.
  • Identifiers validated and ANSI escapes stripped from command output.
Scope. This is designed for a trusted LAN, not the open internet. If you need remote access, put it behind a VPN or an authenticating reverse proxy — don't port-forward it.

Troubleshooting

Common problems

Start with pod doctor — it catches most misconfiguration before you dig further.

SymptomCause & fix
Pods die when you log outLingering is off. loginctl enable-linger $USER.
pod start hangs ~90sPodman 5.0–5.7's network-wait probe. pod masks it automatically on first run; upgrade to 5.8+ to be rid of it.
Agent reports EACCES on its configHost umask or SELinux labelling. pod restart <agent> <inst> re-normalizes permissions from inside the container.
pod update doesn't change the agent versionYou're on an old build where cached layers were reused. Current update defaults to --no-cache; force it with pod prebuild --no-cache.
Dashboard port already in use after reinstallAn orphaned server process. pod server stop sweeps orphans and whatever holds the port.
Agent CLI errors on an unknown flag after an upstream updateThe agent changed its CLI. Check the plugin's wrapper/config in agents/<name>.sh, then pod update <agent>.
pod batch skips an agentThat agent has no AGENT_BATCH_INVOKE (no headless mode) — codehamr, for example. Use it interactively.
Model metadata / context warningsSet POD_DEFAULT_MODEL_CONTEXT_SIZE to your server's real window, then pod restart.

Still stuck? Open an issue with pod doctor output, pod --version, podman --version, and the exact command plus full output.

Upgrading

Staying current

Install methodUpgrade
curl installerpod self-update
Homebrewbrew upgrade pod-agents-manager
dev channelPOD_AGENTS_REF=dev pod self-update

Upgrades replace the CLI and its modules but never your .env or custom agents, skills, flavors, templates, and volume bundles. self-update refuses to move you to an older version than you're running; pass an explicit POD_AGENTS_REF if you deliberately want an older tag.

After upgrading, run pod update to also pull the latest agent CLIs into their images — the manager and the agents version independently.
